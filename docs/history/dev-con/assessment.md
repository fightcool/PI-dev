## 1. 总体判断

PI-dev 已经具备可复现开发、独立 release、实例数据隔离、应用认证、协议回归和浏览器性能验证等基础。它目前是“定制 Agent 工作台 + 环境工程”，尚不是通用多 Agent 运维平台。DEV-CON 的旁路定位正确，但原 M1 同时承担框架移植、认证、三种配置格式、跨文件切换、探测、恢复和审计，低估了写配置这一核心风险。

建议保留愿景，改变依赖顺序：**可信只读视图 → 变更协议与沙箱切换 → 真正消费方接入 → 探测监控 → 资产与运维 → 打包复用**。把配置安全与运行状态的证据做完整，比先铺齐七个模块更有价值。

## 2. 当前整个项目的能力与边界

| 领域 | 已有事实与实现依据 | 对 DEV-CON 的影响 |
| --- | --- | --- |
| 工程入口 | 根 `package.json` 统一 configure、dev、build、测试、PM2、发布检查；root/vendor 分别保留锁文件 | 复用根工程检查；新增 Node 模块无需再引入一套构建框架 |
| 应用主体 | `vendor/pi-web-ui` 0.72.0；Node/TypeScript 服务端、React/Vite 前端、Pi SDK 0.85.1 | DEV-CON 保持独立，避免扩大聊天应用故障范围 |
| 用量与策略 | `vendor/pi-web-ui/lib/usage` 通过 package imports 作为唯一实现 | 不在 dev-con 复制计费、模型策略或流量处理 |
| 开发隔离 | `scripts/dev.mjs` 使用 `.dev`，前端 5173、后端 8890 | 独立目录隔离数据，但父进程环境及 dev 用户权限仍共享，不能称为安全沙箱 |
| 发布与运行 | `scripts/lifecycle/pm2-manager.mjs::pm2Action` 管理 PM2 supervisor；源码与 current/release 分离 | “Pi 服务”必须建模为实例与 manager，不能硬编码旧 UI unit |
| 发布候选 | `scripts/release.mjs` 与 lifecycle 模块实现 shadow 发布/验证/回滚 | 不可直接将 shadow CLI 包装为生产升级按钮 |
| 生产维护 | `docs/PM2-PRODUCTION.md` 明确尚无 production release mode；后续升级需独立维护编排 | 生产升级暂留人工流程；后续先补 job、排空、核验和回滚协议 |
| 排空机制 | `scripts/lifecycle/cutover.mjs::cutover` 等待 activeConversations、pendingMessages | 不能据此保证独立终端作业也已结束；重启要显示影响范围 |
| 状态查询 | PM2 manager 只输出白名单字段，并避免查询 inactive PM2 时新建 daemon | 控制台只读采集也应保持此边界，不暴露 jlist/env/log 原文 |
| 测试 | 根 Node 测试、应用 Vitest、类型检查、自包含协议冒烟、Chromium 性能测试 | 不要用在线模型/真实配置做常规回归；写适配器必须使用夹具 |
| 性能 | `docs/FOUNDATION-VALIDATION.md` 记录长会话渲染显著改善，仍有长任务与大模块 | 历史测量作为基线，不在 DEV-CON 任务内顺带重构聊天内核 |
| 交付限制 | Docker 真实构建验证在既有验收中缺失；Python 3.10 迁移需另排 | “可打包复用”不能仅凭模板存在判定完成 |

根工程、应用、运行版本、工作区和 Agent 私有资源分别有生命周期。控制台应引用它们的标识和能力，不能把相同操作系统用户下的所有路径都视为同一实例。

另有几项应独立进入工程待办，不随本轮控制台开发扩大修改范围：

- `upstream/compatibility.json` 仍写 UI 0.70.0，而当前应用为 0.72.0；`upstream/pi-web-ui.json` 的当前版本上游 SHA 为 null。应补齐可证明的兼容性及来源记录，不能猜测 SHA。
- `scripts/lifecycle/build-target.mjs::assertInactiveCheckout` 以固定 systemd unit 识别在线目录，对手工 Node 或独立 shadow PM2 的覆盖有限；后续构建保护应补失败拒绝和实例覆盖测试。
- `pm2Action` 在 stop 前调用完整 `pm2Options` 校验，配置目录或资源参数异常可能影响紧急停止；应单独评估最小停止依赖。
- 根 CI 对三个依赖域的审计与应用 lint/protocol 检查覆盖并不一致。应区分根、vendor、PM2 锁文件，补必要检查；嵌套 vendor workflow 不会自动成为根仓库 workflow。
- `npm run smoke`、doctor 会使用实例配置；与自包含 `test:smoke` 不同。未来任务面板必须明确检查目标和所需凭据，不能全部标注“隔离测试”。

## 3. Pi 应用的具体接入风险

本节依据应用源码的只读复核，未读取真实配置或执行线上故障复现。它们是 DEV-CON 接入前必须处理的行为与限制，不能视作已发生的线上事故。

| 优先级 | 源码事实 | 接入要求 |
| --- | --- | --- |
| P0 | `server/model-admin.ts::listProviderKeys` 可能从 auth.json 导入并写入密钥库；`activateProviderKey → applyActiveKey` 同时涉及 provider-keys.json、auth.json 和 runtime override | 名为 list 的方法不一定只读；禁止直接用于 M0 采集。适配器列明完整写集合 |
| P0 | `ModelAdminService.listModelsConfig` 返回 `apiKey: p.apiKey`；配置若含明文密钥会进入浏览器 | 新控制面 API 只返回凭据引用；应用既有 API 的密钥回传应单独修复并加测试 |
| P0 | `saveModelConfig` 重建 provider，仅保留部分旧字段；`refreshProviderModels` 保存时省略 apiKey，可能删除旧字段 | 先补无损往返和刷新保留凭据测试，不能直接复用为多 Agent 安全写入器 |
| P0 | `server/index.ts` 的口令登录使用共享口令作为一年期 cookie；有效 Passkey 会话也可能换得该长期 cookie；鉴权依赖 AUTH_TOKEN 非空，口令入口未见限流 | DEV-CON 已采用独立随机短期会话；聊天应用应另排认证修复，统一到期/撤销语义并验证无口令时的暴露边界 |
| P1 | `ClientSession.create` 为客户端建立 sharedModelRuntime；`AgentService.attach` 按 clientId 建会话，未见模型配置的全客户端刷新回执 | 写文件、调用方刷新、其他客户端刷新、新旧对话生效分别验证。项目偏好恢复也应纳入测试 |
| P1 | `saveModelConfig` 使用直接 writeFileSync 并在内部处理异常；外层刷新操作可能继续给成功回执 | 统一错误传递、写入互斥与失败状态；单文件原子写不能替代事务 |
| P1 | `fetchModelsList → probeModelsEndpoint` 只取 /models；15秒定时器在收到响应头后清除，响应体读取没有同一截止时间；缺少体积/并发约束 | 新探测器独立实现全程超时、体积和预算约束，目录可读不等于推理可用 |
| P1 | Skills 来自 agentDir、用户/项目资源与 packages；禁用主要按 name；reload 受活动会话及流式状态影响 | 清单区分来源、路径、配置启用和实际加载，不能仅按同名文件同步 |
| P1 | `server/mcp-bridge.ts` 读取 Web dataDir/mcp.json 的 servers；实现 stdio 桥，缺少 transport 全覆盖、统一取消及完整重连/失败子进程清理 | 不把该桥当成跨 Agent 管理器；静态配置视图与实际启动分别授权，补资源生命周期测试 |

这些能力说明“现有应用已经有设置页面”不等于“可以直接给 DEV-CON 调用”。M1a 应先建立明确的配置所有权与测试夹具；Pi 写入适配器的验收必须覆盖以上故障模式。聊天认证及密钥回传是独立高优先级修复，不能等到全部管理台模块完成才处理。

## 4. 原方案中合理的部分

1. **旁路控制平面**：故障时能管理配置，同时不增加每次模型请求的延迟和单点。
2. **告警后人工切换**：保留成本、能力、数据去向的人工判断，避免失败探测触发自动改配置。
3. **Agent 适配器**：各家协议与文件格式确实不同；差异应该集中在可测试适配器中。
4. **先只读再写入**：插件依赖变更应进入源码与测试链，不由管理台直接 npm install。
5. **配置备份、审计、最小权限**：必要基础；普通用户运行，不授予 sudo，root 运维保留外部流程。
6. **8791 独立端口及独立目录**：与现有在线、候选和开发应用边界一致。
7. **按阶段交付**：长期愿景涵盖渠道、能力资产和系统维护有价值，但必须以验收门槛推进。

## 6. 关键设计优化

**配置变更采用 plan → apply → verify。** plan 绑定 instanceId、配置 revision、目标绑定、字段级脱敏差异、影响与有效期；apply 校验登录/CSRF、计划状态和 revision，同一实例串行执行；verify 分开报告磁盘配置、进程加载及后续会话状态。apply 失败不得返回“切换成功”。

**跨文件事务承认实际能力边界。** 同目录临时文件、权限、fsync/rename、journal 可以恢复崩溃后的部分写入；无法让不参与协议的其他应用同时读到多个文件的原子快照。适配器应优先减少写集合，并为每种格式记录恢复策略。

**公共框架先保持小而明确。** Node 原生 HTTP、固定路由、能力清单、采集函数已足以支撑首期。不要同时造插件运行时、通用表单引擎、事件总线、队列服务和共享 package。出现第二个真实需求再提取公共抽象。

**生产维护由独立任务执行。** 控制台不应通过重启自己的进程树来承载维护事务。未来引入与受维护服务不同的 user job，任务状态可恢复，失败和掉线后仍可查。

**认证是所有阶段共同前提。** 回环绑定之外还需 Host/Origin 校验、会话过期、CSRF、限流、请求体上限、安全 cookie、日志白名单；独立域名上线时另做反代与 Secure cookie 验收。

## 7. 排期建议与本轮交付边界

详细阶段与验收见 [更新后的方案](../../DEV-CON-PROPOSAL.md)。工作量是单人有效开发日的初步估计，包含隔离测试与一次复核，不含等待权限、供应商接口变化和线上维护窗口。

| 阶段 | 估计 | 依赖 | 可交付结果 |
| --- | --- | --- | --- |
| M0 只读基础 | 2–3日 | 根工程 | 登录、仓库版本、服务状态、Agent 能力登记、桌面/移动浏览器验收；本轮实现 |
| M1a 安全变更内核 | 4–6日 | M0 | 凭据引用、revision、计划、单实例锁、备份/恢复、审计；夹具可跑通 |
| M1b 首批渠道切换 | 6–9日 | M1a | Claude、Codex、Pi 分别接入；未知配置保留、认证类型及生效验证；Gemini 保留未支持 |
| M2 监控 | 4–6日 | M1b | 协议探测、预算、SSRF 防护、SQLite 历史、覆盖率与时间线 |
| M3 能力资产 | 6–9日 | M1a | Skills/MCP/提示词先盘点再差异同步，插件只读清单 |
| M4 系统维护 | 5–8日 | M0、独立任务协议 | manager 适配、日志白名单、排空/重启/恢复、工程任务 |
| M5 可复用交付 | 3–5日 | 前述阶段稳定 | 安装、升级、导出排除密钥、干净机器验证、卸载保留数据 |

合计约 30–46 个有效开发日，属于依赖约束下的规划范围，不是承诺交付日期。M3 的只读盘点与 M2 可并行，服务只读观测已前移到 M0。每阶段评审后用实际吞吐重新估算。

首期可在本机实际启动并操作；它没有完成原 M1 的渠道切换，更不代表 M1–M5 全部完工。正式域名、DNS、证书、服务安装及生产切换仍由独立部署任务处理。
