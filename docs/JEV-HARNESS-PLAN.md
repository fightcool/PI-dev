# Jev 在 harness 里怎么用（方案）

> 状态：**方案 + P0 实施中**（2026-09-20）。本文回答两件事：**Jev 到底该在系统里干什么**、**我们现在落了哪几件、还差哪几件**。
> 相关文档：[JEV-DECISION-GATE.md](JEV-DECISION-GATE.md)（门禁内核/判据/阈值/缓存）、[JEV-HOOK.md](JEV-HOOK.md)（提交钩子）、[CONTEXT-POLICY.md](CONTEXT-POLICY.md)（压缩策略：何时压）、[MODEL-ROUTING.md](MODEL-ROUTING.md)（模型路由现状）。

## 0. 一句话

Jev 不是「审稿人」，是**可编程的常识原语**：花一万分之一美元、几百毫秒，换一个校准过的概率，用来替掉贵模型本来要做的语义判断。
把它当闸门只是它最窄的一种用法；**它最大的价值是让 harness 本身变便宜**——少送 token、少上强模型、少返工。

### 1.3 我们自己的 token 账单（说明「钱在哪」）

统计自本仓库开发会话（`agentDir/sessions/--home-dev-PI-dev--/*.jsonl`，2,485,603 字符，≈83 万 token 累计）：

| 类别                                  | 字符占比  | 条数 |
| ------------------------------------- | --------- | ---- |
| **工具结果**（`toolResult: text`）    | **48.8%** | 1166 |
| **模型思考**（`assistant: thinking`） | **48.5%** | 678  |
| 模型输出正文                          | 2.1%      | 227  |
| 用户输入                              | 0.4%      | 25   |

**结论：近一半上下文是工具输出。** 这些 token 会被后续每一轮反复重发（成本随轮数二次增长），而判断「哪一段其实不必送进上下文」正是 Jev 一毛钱能做的事。

## 3. 五期路线（按 ROI 排序）

每期的共同口径：**可开关（默认关）、失败放行、可回退、可量化**。量化只用现成的审计字段（`jev-decisions-cache.jsonl` 的 `audit`）+ 会话级 token 统计，不新建观测体系。

### P0（本轮）：工具结果按需裁剪 —— 打在 48.8% 那块 —— **已实现并实测（2026-09-21）**

> 代码与运维说明：[JEV-TRIM.md](JEV-TRIM.md)。真实会话 dry-run 实测：45,421 字符的测试输出省 **26%**、
> 16,537 字符的文档输出省 **80%**；每次判定 $0.0005-0.001、0.8-3.6s。
> **ROI 取决于 agent 自己的模型单价**（$15/M → ~68×；$3/M → ~13×；$0.042/M → 亏），详见 [JEV-TRIM.md §4.1](JEV-TRIM.md)。

| 项     | 内容                                                                                                                       |
| ------ | -------------------------------------------------------------------------------------------------------------------------- |
| 接入点 | 官方 `tool_result` 钩子（`docs/extensions.md` §tool_result：**可改写结果**，且只作用于**新追加**的那条消息）               |
| 判据   | 一个请求内批量 N 条 `noul`：「该片段对当前目标是否必要？」`state = { objective, tool, sections[] }`                        |
| 省什么 | 工具输出的 token；且因为只改**新消息**，不打断供应商前缀缓存                                                               |
| 量化   | `charsBefore/charsAfter`、保留比例、Jev 成本/延迟 → `<agentDir>/dev-con/jev-trim.jsonl`；先跑 `dry-run` 量「本来能省多少」 |
| 回退   | `JEV_TRIM=off`；任何异常 → 原样放行                                                                                        |
| 风险   | 误删有用内容 → 标记块保留「被省略片段的首行摘要」+ 重取提示；保留比例 >0.8 或省不到 15% 就不动手                           |

### P1：读文件前先重排候选

`rg` 出候选 → Jev 排序 → 只读高分文件（官方 rerank 套路）。省的是「读了整文件才发现不相关」的输入 token。
量化：`files read` 数 / 读入字符数前后对比。

### P2：路由与升级（cascade）

`server/model-routing.ts` 现在是纯规则。在规则**之前**加一层 Jev 判断「这段任务是否需要强模型 / 是否需要开子代理 / 是否需要跑全量测试」，**只在不确定时升级**（官方 cascade：小模型 → 校验 → 必要时才上强模型）。
量化：强模型 token 占比、每任务成本、以及「升级后本可避免」的返工率。风险：把「不确定」定义错 → 要么白省要么漏升级；必须先 `dry-run` 记录「本来会怎么判」。

### P3：通用工具护栏

把护栏从「只拦 `git commit`」扩到 edit/write/破坏性 bash（`rm -rf`、`git push --force`、改生产配置…）。每次 $0.0001，比一次误操作便宜。
量化：拦截次数/误报率（人工回看样本，复用 §9 的复盘流程）。

### P4：轨迹校验（少返工）

回合结束时判断「是否真的完成了用户要求 / 是不是假完成」，早发现早纠偏。省的是**返工**的 token（通常远大于单轮上下文）。
量化：一次通过率、返工轮数、每任务 token。

## 4. 反模式与硬约束（都是踩过或文档明写的）

1. **不改写历史前缀。** 我们自己的 `docs/CONTEXT-POLICY.md §7` 记着：`pi-context-prune` 改写前缀 → 打断供应商前缀缓存 → 已被移除。任何裁剪只能作用于**新进入上下文的内容**（P0 正是因此挂在 `tool_result`）。
2. **失败一律放行，绝不冒充通过。** 与门禁同口径：Jev 不可用/超时/解析失败 → 保持原行为 + 宿主日志留痕；「看着是绿的其实没判」是最危险的失败模式。
3. **别用 agent `while` 循环表达能写成软件流程的东西**（官方架构约束）：Jev 是窄判断，控制流留在代码里。
4. **批量问，不要逐条问**：同一份 state 上的独立问题放一个请求（省 12.2×）。但**有依赖的问题要分第二个请求**。
5. **判据用英文写、放 `instructions`/`criteria`，问题 id 不发给模型**；每条问题足够窄且自洽（见 `JEV-DECISION-GATE.md` §3 的写法约定）。
6. **阈值必须在自己的数据上标定**（官方原话），不能照搬文档示例值。
7. **默认关、可量化再开。** 先 `dry-run` 拿到真实收益，再决定是否默认开启。

## 5. 验收标准

| 期  | 量化目标                                                                               | 失败判据（要回退）                                       |
| --- | -------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| P0  | 大型工具结果平均省 ≥30% 字符；Jev 成本 < $0.001/次；误删有用内容率（人工抽检样本）≤ 2% | 省不到 15%、或抽检发现关键内容被删、或 P99 延迟增加 > 1s |
| P1  | 单任务读入字符数下降，且任务成功率不降                                                 | 多读一轮才拿到所需信息                                   |
| P2  | 强模型 token 占比下降，返工率不升                                                      | 该升级时没升级导致返工                                   |
| P3  | 真实拦截 ≥1 次/周且误报可接受                                                          | 误报导致正常工作被打断                                   |
| P4  | 一次通过率上升 / 返工轮数下降                                                          | 提示变成噪声被忽略                                       |

## 6. 复用约定（避免每个用法重造一遍）

- **统一入口**：`npm run jev -- ask --questions-file <path|-> [--state-file <path|->] [--json] [--raw] [--no-cache]`（`--raw` = 只要原始概率，不套阈值：成功即退出 0，排序/筛选用它）
  - 热路径用**瘦入口** `node --import tsx scripts/jev-ask.ts`（同样的 gate/缓存/审计/source=ask）：实测冷启动
    **~0.65s vs 完整 CLI 2.4s** —— 差距几乎全在 `import "@earendil-works/pi-coding-agent"`（完整 CLI 只用了它的
    `getAgentDir()`）。`agentDir` 是等价复制，有单测与 SDK 逐例对比（漂移即红）。 —— 通用临时命题；与 `check`/`probe` 共用同一个 gate、同一份密钥解析、同一套缓存与审计，退出码 0/1/2/3 语义一致。**新增用法不要再各写一份调用逻辑。**
- **判据要具体到可分**：我们实测同一份 state（一段缓存失败日志 + 一段 CSS + 一段截图流水），
  判据写糊时三个片段都掉到 0.3x（不可分）；改成「引用 `` `sections[i].text` `` + 两侧给真实反例」后，
  相关 0.97 / CSS 0.03 / 截图 0.04（403ms、$0.0000518，三问批量）。**判据质量决定这套用法成不成。**
- 采样 `source` 枚举已有 `check(ci)/probe/tool/ask`，复盘时能按来源看分布（`review export` → 人过标签 → `tune --from-cache`）。
- 密钥只按名字引用（`credentialRef`），任何输出/日志不得出现密钥正文；`state` 正文不落盘。
